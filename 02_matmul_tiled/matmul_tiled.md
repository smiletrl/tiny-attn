
我们先处理一个简单的场景，矩阵乘法的两个矩阵 M, N 都是方阵，即矩阵的行、高相等。

### 问题

在一个原始 gpu kernel 函数中，一个 thread 负责计算 out 中的一个元素。比如

- 坐标为 [2, 30]的thread 会读取 M 第 2 行的所有值，跟 N 第 30 列的所有值，进行计算，得到 out[2][30]的值。
- 坐标为 [2, 29]的thread 会读取 M 第 2 行的所有值，跟 N 第 29 列的所有值，进行计算，得到 out[2][29]的值。

第二行的数据需要被重复读取的次数等于 N 的列数。

为了估算显存的读取复杂度，我们假定矩阵的维度为 n，M 跟 N 的维度都是[n x n]。依据上面的读取流程，M N 中的每个元素都要被读取 n 次。M 共有 n^2 个元素，那么读取复杂度也就是 n * n^2 = n^3. M，N 的读取总复杂度就是 2n^3。

我们希望降低这个显存的读取复杂度，因为每次从全局显存（HBM） 中读取元素都是一次高延迟操作。

### tile 策略

我们考虑两个相同维度[513 x 513] 的矩阵乘法 M x N。得到的结果矩阵Out的维度也是 [513, 513]。

#### 架构

我们采用分块策略（tile 策略），单一tile的维度是 [16 x 16]。我们将一个tile 跟GPU编程里的一个block对应起来。在cpu中启动gpu kernel时，一个block的内部thread维度就是[16 x 16]。而block在grid内部的单一方向维度就是 ceil(513/16) = 33。 在这个例子里，513/16 向上取整，刚好取整数 33 （32+1）, 也就是说，在grid层面，block的维度是[33 x 33]，共有1089个block。

在二维角度上看，比如x方向上，共有 33（num of block） * 16 (num of thread per block) = 528个thread。这个thread的数字显然超过了结果矩阵 Out 在x方向上的513个元素。这意味着有多余的thread 其实是不需要工作的。

我们这么设计的初衷是，用每一个 thread 去计算矩阵 out 中的每一个元素。当这个 thread 的坐标超过 out 的二维坐标时，意味这个 thread 是冗余的。

几个关键变量的定义：

```c++
#define TILE_DIM 16

    // 申请线程块内共享的高速片上内存
    __shared__ float s_M[TILE_DIM][TILE_DIM];
    __shared__ float s_N[TILE_DIM][TILE_DIM];

    int tx = threadIdx.x; // 矩阵的列
    int ty = threadIdx.y; // 矩阵的行

    // 输出矩阵 Out 的全局行列索引
    int row = blockDim.y * blockIdx.y + ty;
    int col = blockDim.x * blockIdx.x + tx;
```

- shared memory s_M, s_N：隶属于一个block。而这个block 就包含了一个完整的 tile，因为它的内部thread维度就是 16 x 16。所以每个thread都可以获取其所在的block的共享内存。 
- s_M 的尺寸是 16 * 16 = 256 个 float。每个 float 是 4 个 bytes （32 位）。s_M 占用的字节数为 256 * 4 = 1024 bytes = 1kb。这里每个 block 的共享内存占用即为 2kb （s_m, s_N）. 共享内存是在片上 SRAM 里分配。以 A100 为例，单个 block 最大可申请 163kb，单个 SM 容量 164KB。共享内存与 L1 cache 共享同一片 SRAM。在这个示例里，共享内存的分配远低于实际限制。
- [ty, tx]: 每个block内部的thread二维索引 [ty, tx]（数值从0到15），表示这个tile/block 16 x 16 里每一个thread。
- [row, col]: 每个thread 坐标[row, col] 是将其所在的block的offset也加进去考虑，得到的是该thread在结果矩阵 out 中所对应的那个元素的坐标。
- [blockIdx.y, blockIdx.x]: block 在 grid 中坐标。 

举例：

- block 的 grid 坐标为[1, 3]。其中一个 thread 的 tile坐标[ty, tx]为[0, 2]。该 thread 的[row, col] 坐标是[1 * 16+0, 3 * 16+2]，即[16, 50]。这个 thread 是有效的，因为 out 的维度是[513， 513]， 坐标数应该 < 513。
- block 的 grid 坐标为[32, 31]。其中一个 thread 的 tile坐标[ty, tx]为[2, 15]。该 thread 的[row, col] 坐标是[32 * 16+2, 31 * 16+15]，即 [514, 511]。这个 thread 的行 514 > 512， 也就是说这个 thread 是无效的。

#### 实现流程

代码

```c++
    float sum = 0.0f;

    // 按 TILE_DIM 沿 K 维度分步滑动推进
    int numTiles = (w + TILE_DIM - 1) / TILE_DIM;
    for (int t = 0; t < numTiles; t++) {
        // 1. 协同协作：每个线程负责将全局显存的一个元素搬运到共享内存
        // M 矩阵边界判断
        int m_col = t * TILE_DIM + tx;
        if (row < r && m_col < w) {
            s_M[ty][tx] = M[row * w + m_col];
        } else {
            s_M[ty][tx] = 0.0f; // 越界填 0，避免影响乘加计算
        }

        // N 矩阵边界判断
        int n_row = t * TILE_DIM + ty;
        if (n_row < w && col < w) {
            s_N[ty][tx] = N[n_row * w + col];
        } else {
            s_N[ty][tx] = 0.0f;
        }

        // 栅栏同步：确保该 Block 内所有线程都已将数据写入 Shared Memory
        __syncthreads();

        // 2. 从共享内存高速读取数据并进行点积累加
        #pragma unroll
        for (int k = 0; k < TILE_DIM; k++) {
            sum += s_M[ty][k] * s_N[k][tx];
        }

        // 栅栏同步：确保所有线程都计算完毕，再开始下一轮 Tile 写入，防止数据覆盖冲突（RAW 冒险）
        __syncthreads();
    }

    // 3. 将最终累加和写回全局显存
    if (row < r && col < w) {
        Out[row * w + col] = sum;
    }
```

1. 分段点积运算

以 out 的元素[15, 49]为例。它是将 M 的第 16 行的数据，跟 N 的第 50 列数据相乘。M 每一行的元素，跟 N 每一列元素的数量都是 513. 在 tile 的策略里，不是一次性将两个矩阵中的 513 个元素都读出来后，一次性计算。而是每次读 16 （num of tile）个元素后，用一个临时存储，保存每个 tile 的计算结果。分段点积运算，最后累加起来。

流程如下：

- 读取 M 第 16 行的（0 - 15）个元素（即从第 1 列到第 16 列的元素）
- 读取 N 第 50 列的（0 - 15）个元素（即从第 1 行到第 15 行的元素）
- 计算分段点积 M[15][0-15] * N [0-15][49] -- 第一轮 tile 循环结束
- 读取 M 第 16 行的（16 - 31）个元素
- 读取 N 第 50 列的（16 - 31）个元素
- 计算分段点积 M[15][16-31] * N [16-31][49]。并且将结果跟上一步的分段点积结果合并相加。 --- 第二轮 tile 循环结束
- 重复以上过程。直到最后一步读完全部数据 M[15][512-527] * N[512-527][49]。不存在的下标元素，比如 M[15][513]的值在计算中以 0 代替，这样保持计算过程统一
- 最终将所有分段点积合并后的结果，作为 Out[15][49] 的值保存到显存中。

2. 读取数据拆分

在一个 block/tile 内，有 16 x 16 个 thread。这个 block 内的所有thread 通过屏障 `__syncthreads()` 一次性读取M/N 16 x 16个元素. 读取的元素保存在共享内存中。

一个 thread 的[row, col]坐标，跟 [ty, tx] 坐标同时发挥作用，决定了每轮 tile 循环中 thread 读取的具体元素。

假定 M N 的矩阵点积计算的坐标形式 M[i][k] * M[k][j]，那么我们在数据读取的拆分过程中，沿着 k 方向前进。

以 blockIdx 坐标[2, 3] 为例。内部的 thread [row, col]坐标区间，行方向(32 - 47), 列方向(48 - 63). 

- 读取 M 行方向 (32 - 47), 列方向（0 - 15）
- 读取 N 行方向（0 - 15），列方向（48 - 63）
- 将读取出来的两组 16 x 16 的 元素进行上面步骤的分段点积运算  -- 第一轮 tile 循环结束
- 读取 M 行方向 (32 - 47), 列方向（16 - 31）
- 读取 N 行方向（16 - 31），列方向（48 - 63）
- 将读取出来的两组 16 x 16 的 元素进行上面步骤的分段点积运算 -- 第二轮 tile 循环结束
- 重复以上过程，直到最后一个 tile 读完。下标超过矩阵范围的，设定默认值 0。

在上面的每轮循环中，一个 thread 读取 M 跟 N 中的一个元素，并且将读取的元素覆盖在共享内存的坐标位置[ty, tx]的元素。这样这个 block 内全部的 thread都只需要分别读取 M/N 一次。原来需要读取 16 次，现在只需要 1 次。

通过上面的策略，我们将 out 的行方向(32 - 47), 列方向(48 - 63)的元素就全部计算出来了。


对于 blockIdx 坐标[2, 4]的 block。内部的 thread [row, col] 坐标区间，行方向(32 - 47), 列方向(64 - 79). 当我们重复类似上面的 tile 循环过程，显然 M 的数据有重复读取。

- 读取 M 行方向 (32 - 47), 列方向（0 - 15）
- 读取 N 行方向（0 - 15），列方向（64 - 79）
- 将读取出来的两组 16 x 16 的 元素进行上面步骤的分段点积运算  -- 第一轮 tile 循环结束

可见这个 tile 策略并不是让每个元素完全只读一次。

**通过这个 tile 策略，整体的显存读取复杂度为 1/16 x（2n^3）。降为了原始复杂度的 1/16.**

以该 Block 内部坐标为 `[ty=2, tx=5]` 的某一个线程为例。它在 $t=1$ 时同时承担两项数据搬运工作：

```text

    全局列: m_col = 1*16 + 5 = 21

 2. 搬运 N 的元素到 s_N：
    全局行: n_row = 1*16 + 2 = 18
    全局列: col = 48 + 5 = 53
    全局显存读取: N[18][53]  ───────────────► 写入片上 s_N[2][5]

-------------------------------------------------------------
 全景对应：Block 内 256 个线程并发执行上述指令，
 刚好严丝合缝地填满 s_M 和 s_N 的 256 个空位：

   线程 [2,5]   搬运并写入 ──> s_M[2][5]  与  s_N[2][5]
```

### 图 4：为什么相邻 Block 会产生重复读取（数据冗余的可视化）

把 `Block[2, 3]` 和它的右邻居 `Block[2, 4]` 放在一起对比：

```text
 Block[2, 3] 计算 Out[32~47, 48~63]        Block[2, 4] 计算 Out[32~47, 64~79]
 ──────────────────────────────────       ──────────────────────────────────
 两个 Block 的行网格号相同 (blockIdx.y 都是 2)，因此行坐标全都是 row ∈ [32~47]

 t = 0 时：                               t = 0 时：
 * 读 M: [32~47][ 0~15]  ◄── 完全相同 ──► * 读 M: [32~47][ 0~15]
 * 读 N: [ 0~15][48~63]                   * 读 N: [ 0~15][64~79]

 t = 1 时：                               t = 1 时：
 * 读 M: [32~47][16~31]  ◄── 完全相同 ──► * 读 M: [32~47][16~31]
 * 读 N: [16~31][48~63]                   * 读 N: [16~31][64~79]

 结论：
 这一横排所有的 Block（共有 33 个），在每一轮迭代中都会向全局显存重复请求同一份 M 的切片。
 矩阵 M 的这块数据总共被读取了 33 次（即被列维度的 Block 数量放大），
 这就是复杂度中无法彻底消除、但被压缩为原来 1/16 的“残余冗余读取”。
```
