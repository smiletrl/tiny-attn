# Bank conflict

在 GPU 架构中，**Bank（存储体）** 是共享内存（Shared Memory）内部在物理上划分出的独立存储单元。

---

### 1. 为什么要有 Bank？

GPU 是以 **Warp（32 个线程）** 为最小执行单元并发读写内存的。
如果让 32 个线程同时去读取或写入同一个单端口存储器，硬件在同一个时钟周期内只能处理一个请求，其余线程只能排队等待，延迟会非常高。

为了解决这个问题，硬件工程师把一块连续的共享内存物理切分成了 **32 个独立、并行的存储体（Bank 0 到 Bank 31）**。

* 每个 Bank 每个时钟周期可以独立服务一个 32-bit（4 字节）的数据读写。
* 如果 Warp 内的 32 个线程**分别访问 32 个不同的 Bank**，这 32 个请求就能在**同一个时钟周期内完全并行完成**，达到理论最大带宽。

---

### 2. 连续地址与 Bank 的映射规则

在现代 NVIDIA GPU（从 Kepler 架构至今）中，共享内存的地址是按照 **4 字节（一个 `float` 的大小）轮流交替分配到 32 个 Bank** 中的：

$$\text{Bank 编号} = \left(\frac{\text{字节地址}}{4}\right) \pmod{32} = \text{float 数组下标} \pmod{32}$$

例如定义数组 `__shared__ float s_data[128];` 时，各元素所处的物理 Bank 如下：

| 元素下标 | 对应地址偏移 | 所属 Bank |
| --- | --- | --- |
| `s_data[0]` | 0 ~ 3 字节 | **Bank 0** |
| `s_data[1]` | 4 ~ 7 字节 | **Bank 1** |
| `s_data[2]` | 8 ~ 11 字节 | **Bank 2** |
| ... | ... | ... |
| `s_data[31]` | 124 ~ 127 字节 | **Bank 31** |
| `s_data[32]` | 128 ~ 131 字节 | **Bank 0**（回到 0 号） |
| `s_data[33]` | 132 ~ 135 字节 | **Bank 1** |

---

### 3. 什么是 Bank Conflict（存储体冲突）？

当同一个 Warp 内的**两个或多个不同线程**，试图在**同一个周期内访问同一个 Bank 中不同的内存地址**时，就发生了 **Bank Conflict**。

* **后果**：硬件无法在单周期内同时读取同一 Bank 内的不同地址，只能将冲突的请求**串行化（排队依次处理）**。
* **代价**：
* 如果有 2 个线程命中同一个 Bank 的不同地址，称为 **2-way 冲突**，访存耗时变成 2 倍。
* 如果有 8 个线程命中同一个 Bank，耗时变成 8 倍。
* 最坏情况下 32 个线程全撞在同一个 Bank 上（32-way 冲突），访存性能直接跌去 97%。



> **注意一种特殊情况——广播（Broadcast）**：
> 如果同一个 Warp 内的多个线程访问的是**同一个 Bank 里的同一个地址（相同的数据）**，硬件会直接通过单次广播把数据分发给它们，**不会产生冲突**。

---

### 4. 对应矩阵乘法中的代码理解

在前面的矩阵乘法中，声明了如下共享内存：

```cpp
__shared__ float lhs_s[128][32];

```

由于它的行宽刚好是 **32** 个 float：

* 第 0 行的第 0 列 `lhs_s[0][0]` 落在 **Bank 0**。
* 第 1 行的第 0 列 `lhs_s[1][0]` 物理下标是 `1 * 32 + 0 = 32`，模 32 后依然落在 **Bank 0**！
* 第 2 行的第 0 列 `lhs_s[2][0]`（下标 64）依然落在 **Bank 0**！

这意味着：**在 `[128][32]` 的排布下，整列上的所有元素，物理上全都在同一个 Bank 里面！**

* 如果一个 Warp 的各个线程按列往下读取（例如线程 0 读第 0 行第 0 列，线程 1 读第 1 行第 0 列），就会全部撞在 Bank 0 上，造成严重的串行化停顿。
* 因此在读取计算时使用了行方向向量化、错峰起始偏置 `si_start` 等技巧，就是为了把 Warp 各线程访问的地址分散到不同的 Bank，避免串行排队。
